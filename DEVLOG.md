## 2026-10-06 — Шаг 0: окружение и каркас

**Окружение.** WSL2, Ubuntu 24.04 (noble), Python 3.12. ROS 2 Jazzy поставлен
из официального apt-репозитория (`ros2-apt-source`): `ros-jazzy-desktop`,

**Решения:**

- Карта `map.yaml/map.pgm` скопирована в `src/did_agent/maps/` из
  `ROBOTIS-GIT/turtlebot3@jazzy` (Apache-2.0), чтобы тесты работали без установленного ROS.
  Пакеты turtlebot3 не правим.

## 2026-10-06 — Шаг 1: карта, карта стоимостей, A*, путевые точки (core)

**Проверили утверждение TASK.md «карта совпадает с мировыми координатами»** —
нашли на `map.pgm` связные компоненты препятствий: 9 столбов с центрами в
{−1.1, 0, 1.1}² с точностью ≤ 0.04 м (< 1 клетки), арена в пределах ±2.7 м,
точка старта (−2.0, −0.5) свободна. Внутренности столбов на карте `unknown`
(лидар их не видел) → **unknown считаем препятствием**.

**Модули:**
- `frames.py` — odom ↔ world (`x_w = −2.0 + odom.x`, `y_w = −0.5 + odom.y`), углы, кватернион → yaw.
- `grid_map.py` — свой парсер PGM (P5/P2) + `map.yaml` в режиме map_server *trinary*.
  Конвенция: `occ[iy, ix]`, `iy = 0` — нижняя строка (мировая y растёт вверх); картинку переворачиваем при загрузке.
- `costmap.py` — два слоя:
  - `lethal`: препятствия, раздутые на **0.2 м от центра робота** (так трактуем «запас около 0.2 м»;
    радиус Burger ≈ 0.105 м, остаётся ≈ 0.1 м зазора);
  - `cost = base × terrain`: `base` — мягкая полоса 0.2–0.35 м у стен с множителем 2
    (робот держится середины проходов), `terrain` — **обновляемый слой** грунтов
    (`set_terrain_rect/circle`, `reset_terrain`) для уровней 3–4.
- `astar.py` — 8-связный A*, без срезания углов у препятствий. Стоимость ребра =
  длина × среднее множителей двух клеток; все множители ≥ 1, поэтому октильная
  эвристика допустима. `plan_world` подтягивает старт/цель, попавшие в запас, к ближайшей свободной клетке.
- `path_utils.py` — лестница клеток → редкие путевые точки: жадное «прямая видимость»,
  причём срезка принимается, только если прямой отрезок **не дороже** исходного участка пути —
  иначе упрощение срезало бы дорогие грунты.

**Доказательство:** `pytest` — 29 passed за 1.2 с. На реальной карте путь
старт → (1.6, 1.6): 84 клетки за 8 мс → 9 путевых точек, 4.67 м (ASCII-рендер в истории сессии).

**Заметка на потом:** из-за мягкой полосы у стен упрощение иногда оставляет лишние
близкие точки; на езду не влияет, при необходимости поднимем `tolerance` в `simplify`.

## 2026-10-07 — Шаг 3: свой sim-launch без окна Gazebo + RViz

**Проблема:** окно Gazebo в WSLg не работает на этой машине (Intel Arc 140T):
- по умолчанию Mesa выбрала программный рендер (`llvmpipe`, 8 потоков) — окно показывало только робота, Sim time = 0, не обновлялось;
- с `GALLIUM_DRIVER=d3d12` окно открылось, но вместо сцены — цветные артефакты (Ogre2 + d3d12).
Ещё нюанс: в `turtlebot3_world.launch.py` у GUI стоит `on_exit_shutdown: true` — закрыли окно, умерла вся симуляция.

**Решение:** `did_agent/launch/sim.launch.py` собирает **тот же** мир из тех же частей turtlebot3_gazebo
(тот же `.world`, `spawn_turtlebot3.launch.py` с x=−2.0, y=−0.5, тот же мост, robot_state_publisher),
но: сервер без окна, GUI по флагу `gui:=true` и без убийства симуляции при закрытии;
плюс `map_server` с нашей картой, статический TF `map → odom` = (−2.0, −0.5) и RViz (карта, модель, лидар, одометрия).
Пакеты turtlebot3 не правим. RViz рендерит через GPU (llvmpipe-потоков нет); в лог пишет предупреждение шейдера Map-дисплея — проверяем глазами.

**Находка: одометрия врёт при упоре в препятствие.** Teleop оставили ехать 0.1 м/с; робот упёрся в стену арены.
`/odom` (через TF) показал x_world = **7.04 м** (за стеной), Gazebo ground truth — (2.19, 0.98), робот развёрнут и наклонён.
Колёсная одометрия интегрирует прокрутку колёс.
→ **Судья считает всё (путь для батареи, столкновения, расстояние до образцов, базу) по истинной позе из Gazebo**, а не по `/odom`.
→ Агенту это урок для уровня 4: скачок одометрии без изменения `/scan` — признак упора/проскальзывания.

## 2026-10-07 — Шаг 4: судья и генератор сценариев

**core (без ROS):**
- `scenario.py` — Scenario/Sample/Zone(circle|rect)/Event, YAML ↔ объект, генератор `generate(difficulty, seed, grid)`:
  образцы ставятся только в клетки, **достижимые от базы** (заливка по карте с запасом 0.25 м), ≥ 0.8 м от базы, ≥ 0.6 м друг от друга;
  зоны грунта — круги r 0.35–0.6 м с множителем 2–4; опасные зоны не накрывают образцы и базу;
  hard: 3 скрытых события — смена множителя зоны (~50–80 с), новая опасная зона (~100–140 с), сбой датчика (шум 0.2 на 60 с, ~160–200 с).
  Детерминизм: `random.Random(seed)` → одинаково на Windows и Linux.
- `battery.py` — расход = 1.0/м × множитель грунта + 0.05/рад + 0.005/с; не уходит в минус.
- `sensor.py` — `exp(−d/0.7) + N(0, 0.03)`, обрезка [0, 1], без направления.
- `judge.py` — вся логика судьи: батарея по истинной позе (множитель — по середине шага), столкновение = центр робота ближе 0.125 м к препятствию карты
  (одно событие на касание), опасные зоны (штраф на входе, шум датчика ×3 внутри), скрытые события по времени,
  `collect` (< 0.30 м, иначе false_collect), `finish`, JSON счёта **без координат образцов/зон**, приватный журнал для разбора.
- Все параметры, которых нет в TASK.md, — в `config/judge.yaml` со ссылками на QUESTIONS.md; опечатка в ключе конфига — ошибка, а не тихий дефолт.

**Истинная поза для судьи.** `ros_gz_bridge` при конверсии `Pose_V → TFMessage` теряет имена сущностей (child_frame_id пустой),
поэтому судья читает `/world/default/dynamic_pose/info` напрямую через Python-биндинги gz-transport (идут в ROS Jazzy) — ~59 Гц, с именем `burger`.
Обёртка `nodes/gz_pose.py`; при недоступности — откат на `/odom` с ошибкой в лог.

**ROS:** `nodes/judge_node.py` — тонкая обёртка; `launch/did.launch.py scenario:=easy|medium|hard|file.yaml seed:=N` — симуляция + судья одной командой.
Сценарии easy/medium/hard (seed 42) лежат в `scenarios/`; генерация: `python3 -m did_agent.gen_scenario hard --seed 7 -o x.yaml`.

**Доказательство:** pytest — 77 passed. В живой симуляции: топики `/did/battery|sample_sensor|score|events`, сервисы `/did/collect|finish` (Trigger);
`/did/collect` на базе → `success=False, "no sample within 0.30 m"` + событие `false_collect` (−2);
проезд 0.54 м → батарея 59.78 → 59.19. **Уровень 0 пройден.**

**Урок процесса:** длинные записи в DEVLOG через `bash -lc '... <<EOF'` ломаются на одинарных кавычках
в тексте — DEVLOG обрезался, коммит не прошёл. Дальше пишем документы редактором файлов, а коммиты — через `git commit -F файл`.

## 2026-10-07 — Шаг 5: навигация (уровень 1) и сквозной прогон easy

**core (без ROS):**
- `controller.py` — следование по путевым точкам: поворот на месте при ошибке курса > 0.6 рад, иначе езда
  с П-регулятором курса; замедление перед последней точкой; ограничения Burger (0.22 м/с; угловую держим 1.8 из 2.84 рад/с —
  меньше проскальзывания) и ограничение ускорений. `front_clearance` — минимум лидара в конусе ±0.5 рад.
- `navigator.py` — A* → точки → follower; стоп/замедление по лидару (0.16 / 0.35 м); нет прогресса 15 с → перепланирование (до 3 раз) → `failed`.
  `path_cost` — длина пути × множитель грунта из слоя `terrain` (оценка расхода батареи).
- `mission.py` — граница «кто решает / кто исполняет»: `Subgoal(explore|goto|collect|return|finish, target, reason)`,
  протокол `Planner(next_subgoal, on_result)`, `AgentState`. `ScriptedPlanner` — базовый план уровня 1.
  LLM-планировщик (уровень 2) = ещё одна реализация `Planner`; ничего ниже не меняется.
- `executor.py` — исполняет подцели; **сам оценивает расход батареи на метр** по наблюдениям (`/did/battery` / пройденный путь)
  и **отказывает в поездке**, если после неё не хватит заряда вернуться (запас ×1.3 + 1.0). Эта страховка не зависит от планировщика —
  важно, когда подцели начнёт выдавать LLM.
- `offline_sim.py` — кинематика + настоящий судья + настоящая карта: вся миссия за секунды без ROS/Gazebo
  (`python3 -m did_agent.core.offline_sim easy`). Для тестов и для разработки LLM-планировщика на Windows.

**Тест нашёл реальную дыру:** при батарее 9 робот разряжался посреди переезда — решение «домой» принималось только между подцелями.
Исправлено проверкой бюджета поездки в исполнителе (см. выше).

**ROS:** `nodes/agent_node.py` — тонкая обёртка: `/odom`, `/imu`, `/scan`, `/did/*` → `MissionExecutor` → `/cmd_vel` (TwistStamped),
`/did_agent/path` (RViz), `/did_agent/journal`, вызовы `/did/collect`, `/did/finish`. Журналы прогона — в `runs/`.
Грабли: атрибут `self.executor` в узле конфликтует с `rclpy.Node.executor` → переименован в `self.mission`.

**Сквозной прогон в Gazebo одной командой** `ros2 launch did_agent did.launch.py scenario:=easy`:
3/3 образца, возврат на базу, 0 штрафов, батарея 48.4 из 60, счёт 34.84 за 63 с симуляции.
Офлайн-симулятор на том же сценарии дал 34.85 — модели согласованы.

**Находка: дрейф курса одометрии.** Судья фиксировал сбор s2 в 0.28 м от цели (радиус сбора 0.30 — прошли впритык), хотя в конце пути
ошибка позиции всего 4 см. Причина — ошибка **курса** 0.1 рад (проскальзывание на разворотах): она даёт смещение, пропорциональное
расстоянию от старта (0.1 × 2.9 м ≈ 0.29 м). Курс IMU совпадает с истинным до 0.001 рад.
→ `core/localization.py`: путь берём из одометрии, курс — из IMU. Ошибка в точках сбора: **0.14 / 0.28 / 0.23 → 0.06 / 0.05 / 0.05 м**.
Оговорка для питча: IMU в симуляции без шума; на реальном роботе нужен фильтр (EKF/robot_localization) или AMCL по лидару.

**Тесты:** 98 passed (навигация по реальной карте без касаний, лимиты Burger, отказ при недостижимой цели,
офлайн-миссии easy + 3 сгенерированных medium, ранний возврат при низком заряде, дрейф курса).

## 2026-10-07/08 — Шаг 6: стабильность в WSL, ручной режим, подготовка к защите

**Чёрный экран при запуске.** RViz падал (segfault): шейдер Map-дисплея не линкуется на драйвере d3d12 (WSLg + Intel Arc),
после чего драйвер сбрасывал устройство (`D3D12: Removing Device`) — экран чернел. Плюс пользователь запускал поверх нашей
незакрытой симуляции (два сервера Gazebo делят gz-transport-топики).
→ RViz на программном рендере (`LIBGL_ALWAYS_SOFTWARE`, только для RViz); launch отказывается стартовать, если Gazebo уже запущен;
`scripts/stop_sim.sh`; узлы корректно выходят по Ctrl+C (`ExternalShutdownException` в rclpy Jazzy).

**Новые требования к показу** (карта, положение на карте, задать точку/маршрут, движение, полный сценарий):
- `planner:=manual` — `GoalQueuePlanner`: RViz «2D Goal Pose» = ехать сейчас (вытесняет текущую поездку),
  «Publish Point» = добавить точку маршрута, цель на базе = вернуться и `/did/finish`. Скрипты `send_goal.sh`, `send_route.sh`.
- Маркеры в RViz: карта (дублирует Map-дисплей на случай проблем с шейдером), «вид судьи» (образцы, зоны, база), маршрут и поза агента.
- Агент публикует TF `map→odom` из своей позы (одометрия + IMU), как AMCL/SLAM: до этого RViz рисовал скан по сырой одометрии,
  и лидар «съезжал» с карты. После — точки лидара лежат на стенах весь прогон.
- Судья пишет истинную траекторию в журнал прогона.

**Грабли:** цвет маркера целыми числами `(1, 1, 1, 1)` роняет весь процесс через assert в C-коде rosidl (не исключение!) —
`float()` в одном месте. Аргумент launch, использованный до объявления, — тоже ошибка запуска.

**Скриншоты без доступа к экрану:** ассистент снимает только окно RViz через Win32 `PrintWindow` (`docs/img/`).

**Результаты:** Gazebo — easy 3/3, medium 5/5, оба с возвратом и без штрафов (34.84 и 54.68); ручной маршрут (цель + 3 точки + домой) — без штрафов.
Офлайн по 10 сценариев каждого уровня — 100 % образцов, 10/10 возвратов, 0 столкновений; в hard 11 заездов в опасные зоны (агент их пока не знает — уровень 4).
Расход на метр по переездам easy: 1.11 / 1.70 / 1.15 / 1.11 — скачок ровно на переезде через зону A (×3.4): батарея выдаёт дорогой грунт (гипотеза H1).
Тесты: 104 passed. Резюме для защиты — `docs/DEFENSE.md`.

## 2026-10-08 — Шаг 7: LLM-планировщик (уровень 2)

**API.** ai.mai.ru — OpenAI-совместимый (`/v1/chat/completions`). Ключ лежит в `.env` (в `.gitignore`), читается клиентом
`core/llm_client.py` (только стандартная библиотека), никогда не печатается (`repr` скрывает ключ); перед коммитом — поиск ключа по репозиторию.
Все доступные чат-модели — «думающие»: сначала `reasoning_content`, потом ответ.

**Эксперимент 1 — модель считает геометрию сама.** Промпт с координатами образцов и зоны («обойди зону A»):
все 6 моделей исчерпали 800, а потом и 4000 токенов на рассуждения (37–77 с) и **ни одна не вернула JSON**.
→ Решение: **геометрию считает алгоритм.** A* даёт стоимость каждого переезда (робот↔цели↔база) × измеренный расход на метр;
модель получает таблицу и ссылается на цели по id — выдумать координаты она не может.
Повтор сравнения: **все 6 моделей вернули корректный JSON**; быстрые — за 5–7 с. Выбрана `deepseek-v4.1-flash` (5.5 с, полный план).
Две модели Qwen вернули обрывок плана (`goto s1` и всё) — валидатор это ловит и достраивает.

**Эксперимент 2 — жёсткий бюджет (battery 10).** Модель начала перебирать комбинации целей (задача о рюкзаке) и 3 раза подряд
упёрлась в лимит токенов (по 30 с, пустой ответ) → сработал резервный план. Робот вернулся без штрафов, но ждал 90 с.
→ Решение: **комбинаторику тоже считает алгоритм** — точное ДП по подмножествам (Held–Karp, ≤ 2^n·n состояний) даёт для каждого
числа образцов самый дешёвый выполнимый порядок; модель выбирает из 2–4 ВАРИАНТОВ стратегию (больше образцов или больше запас)
с учётом наблюдений и объясняет. Результат: **4.5 с и 278 токенов вместо 3×30 с**; модель выбрала 3 образца из 5 и вернулась с запасом.
Пустой ответ с `finish_reason=length` теперь даёт модели конкретную обратную связь («не перебирай, выбери вариант»).

**Устройство `core/llm_planner.py`:**
- промпт: миссия, причина планирования, состояние (заряд, резерв, «доступно для плана», измеренный расход/м), таблица целей,

- перепланирование: план кончился; подцель не удалась; штраф судьи; переезд дороже прогноза в 1.4 раза (сигнал дорогого грунта —
  задел уровней 3–4); «целей не осталось» — без вызова модели;

- журнал каждого вызова: причина, промпт, варианты, ответ, рассуждение модели, задержка, токены, отклонения → `runs/*_agent.json`, `/did_agent/llm`.

## 2026-10-08 — Шаг 8: веб-пульт на localhost

`./scripts/control_panel.sh` → http://localhost:8080 (Windows-браузер видит сервер из WSL по localhost).
- **Сервер** `did_agent/webui/server.py` — только стандартная библиотека Python (aiohttp/websockets в WSL нет):
  `ThreadingHTTPServer` + Server-Sent Events (живые данные 4 раза в секунду), внутри — ROS-узел (подписки на `/did/*`,

  `ros2 launch did_agent did.launch.py ...` подпроцессом (лог в кольцевом буфере, остановка — SIGINT группе + `stop_sim.sh`).
  Слушает только 127.0.0.1, все параметры запуска проверяются (сценарий, режим, заряд, модель — из списка).
- **Страница** `webui/index.html` — без внешних библиотек и CDN: карта на canvas (клетки карты + запретная зона, зоны,

  телеметрия, график заряда (одна серия, подсказка при наведении), лента событий/подцелей, панель LLM (мысль, план,
  попытки, отклонения; модалка с промптом, ответом и рассуждением модели), лог, история прогонов из `runs/`.
- **Агент:** топик `/did_agent/state` (JSON: поза, путь, маршрут, режим, «думает ли LLM», лидар в мире) и `/did_agent/cancel`;

**Сбор образцов в ручном режиме** (вопрос команды: «в чём смысл маршрута вручную, если робот не собирает образцы?»).
Собирать на каждой точке нельзя — `/did/collect` без образца рядом даёт штраф −2. Решение — по датчику, который агенту положен по интерфейсу:
доехав до точки, `GoalQueuePlanner` смотрит сглаженный (~0,8 с) `/did/sample_sensor`; ≥ 0,6 (≈ ближе 0,3 м) → подцель `collect`, иначе — дальше без попытки.
Плюс «Собрать здесь» (`/did_agent/collect_now`) и выключатель автосбора (`/did_agent/auto_collect`), индикатор датчика на пульте.
Это первый шаг к уровню 3 (поиск по датчику). Порог 0,6 подобран по модели датчика судьи (exp(−d/0,7)) — на уровне 3 агент должен оценивать его сам.
Gazebo: цель рядом с s5 → датчик 0,99 → собран; цель вдали → попытки нет, штрафа нет; автосбор выкл → у s4 (датчик 0,77) не собирает, «Собрать здесь» → собран.
Грабли: старый сервер пульта не завершался по SIGINT и держал порт → новый падал с трейсбеком. Теперь — понятное сообщение о занятом порте
и корректная остановка по SIGINT/SIGTERM. Тесты: 122 passed.
