# Резюме проекта для защиты — команда IKA, DID Hack 2026

## 1. Одной фразой

**Робот TurtleBot3 в симуляторе Gazebo сам строит маршрут по карте, объезжает препятствия, собирает образцы, следит за батареей и возвращается на базу; оператор может в любой момент задать ему точку или маршрут прямо на карте.**

## 2. Задача и цель

- Задача DID Hack: «автономный ИИ-исследователь» — агент на TurtleBot3 Burger в мире `turtlebot3_world` (шестиугольная арена, 9 столбов) ищет скрытые образцы, выясняет, какие участки пола «дорогие» по расходу батареи, и возвращается на базу до разрядки.
- Уровни задачи: 0 — среда, 1 — навигация, 2 — LLM-планировщик, 3 — научный цикл (гипотезы, поиск по датчику), 4 — адаптация к меняющейся среде.
- **Цель на сегодняшнюю защиту:** работающий прототип: карта → положение робота на карте → постановка задачи (точка/маршрут/миссия) → движение → результат. Это уровни 0–1 плюс задел под 2–4.

## 3. Что показываем на демо (сценарий, ~3 минуты)

Перед демо: `cd ~/innopolis_proj && source install/setup.bash && ./scripts/stop_sim.sh`

### Шаг 1 — запуск одной командой (ручной режим)
```bash
ros2 launch did_agent did.launch.py planner:=manual
```
Говорим: «Одна команда поднимает Gazebo с миром без изменений, нашего судью, агента и RViz».
Через ~10 с в RViz видно:
- **карта** арены (статичная карта из `turtlebot3_navigation2`), бордовая полоса — запретная зона 0,2 м вокруг стен и столбов;
- **робот** на базе (зелёный круг BASE), **красные точки лидара** ровно на стенах — значит, робот правильно знает своё положение;
- «вид судьи»: жёлтые шары — образцы, оранжевый круг — дорогой грунт с множителем (×3,4).

### Шаг 2 — постановка задачи: точка назначения
В RViz кнопка **2D Goal Pose** → кликнуть в свободное место (например, справа внизу между столбами).
Говорим: «A* строит путь по карте стоимостей (голубая линия), путь превращается в путевые точки, контроллер ведёт робота командами скорости в `/cmd_vel`».
Запасной вариант без мыши: `./scripts/send_goal.sh 0.55 -0.55`.

### Шаг 3 — маршрут из нескольких точек
Кнопка **Publish Point** → 3 клика по карте. Появятся голубые пронумерованные точки, робот проходит их по порядку.
Можно посреди движения дать новую **2D Goal Pose** — робот бросит текущую поездку и поедет к новой цели (вытеснение цели).
Запасной вариант: `./scripts/send_route.sh 0.55,0.55 -0.55,1.6 -1.6,0.55`.

### Шаг 4 — результат
**2D Goal Pose на зелёный круг BASE** → робот возвращается и вызывает `/did/finish`. В терминале — итог судьи (JSON): батарея, путь, штрафы.

### Шаг 5 — полный автономный сценарий (если есть время / показать запись)
```bash
./scripts/stop_sim.sh
ros2 launch did_agent did.launch.py scenario:=easy
```
Робот сам едет к 3 образцам, на каждом вызывает `/did/collect` (образец становится серым), возвращается на базу и вызывает `/did/finish`. **~65 секунд симуляции, 3/3, 0 штрафов, счёт 34,84.** `scenario:=medium` — 5 образцов, ~90 с.

### Если что-то пошло не так
| Симптом | Что делать |
|---|---|
| `Gazebo simulation is already running` | `./scripts/stop_sim.sh` и запустить снова |
| Окно RViz пустое/чёрное | подождать 10–15 с (программный рендер); закрыть RViz и `ros2 run rviz2 rviz2 -d install/did_agent/share/did_agent/rviz/did.rviz` |
| Робот не реагирует на клик | проверить, что запущено с `planner:=manual`; в режиме миссии цели из RViz игнорируются (в логе предупреждение) |
| Нужно показать без живого запуска | скриншоты `docs/img/`, логи `runs/` |

## 5. Архитектура

```
Gazebo (turtlebot3_world, без изменений)
   │ /odom /imu /scan /clock                       ▲ /cmd_vel (TwistStamped)
   ▼                                               │
did_agent  ── Planner ─(подцели)→ MissionExecutor ─→ Navigator (A* + контроллер)
   │           scripted | manual   бюджет батареи      стоп по лидару
   │           (LLM — уровень 2)   журнал подцелей
   │ /did/collect, /did/finish (Trigger)
   ▼
did_judge  — батарея, датчик образцов, столкновения, штрафы, скрытые события
   │ истинная поза из Gazebo (gz-transport)
   └→ /did/battery /did/sample_sensor /did/score /did/events
```

**Главные решения (и почему):**
1. **Вся логика — чистый Python без ROS** (`core/`, ~1 560 строк), узлы ROS — тонкие обёртки. Можно разрабатывать и тестировать на Windows; 104 автотеста за ~25 с; отдельный тест падает, если в core кто-то импортирует rclpy.
2. **Подцель — граница «кто решает / кто исполняет».** Планировщик выдаёт `explore | goto | collect | return | finish`, исполнитель их выполняет. LLM-планировщик (уровень 2) — просто ещё одна реализация интерфейса `Planner`, остальное не меняется. LLM никогда не управляет скоростью напрямую.
3. **Страховка в исполнителе, а не в планировщике:** перед каждой поездкой он проверяет, хватит ли батареи доехать и вернуться (запас ×1,3). Работает при любом планировщике, в том числе при ошибке LLM.
4. **Судья считает по истинной позе из Gazebo**, агент — по своим датчикам. Иначе ошибки одометрии «подыгрывали» бы агенту.
5. **Офлайн-симулятор** (кинематика + настоящий судья + настоящая карта): вся миссия за секунды без Gazebo — для тестов и разработки планировщиков.

## 7. Логика карты и движения

**Карта.** Готовая карта `map.pgm` (384×384 клеток по 5 см). Проверили, что она совпадает с координатами Gazebo: нашли на ней 9 столбов — их центры в {−1,1; 0; 1,1}² с точностью < 4 см. «Неизвестные» клетки (внутри столбов) считаем препятствием.

**Карта стоимостей** — два слоя:
- запретный: препятствия, раздутые на **0,2 м от центра робота** (радиус Burger ≈ 0,105 м → ~10 см зазора);
- стоимость клетки: мягкая полоса у стен (×2 — держаться середины прохода) × слой «грунтов», который можно обновлять во время работы (уровни 3–4).

**Планирование — A\*** по сетке, 8 направлений, без срезания углов у препятствий; цена шага = длина × множитель стоимости. ~10 мс на всю арену.

**Путь → путевые точки:** лестница клеток упрощается до прямых отрезков; отрезок-срезка принимается, только если он не дороже исходного участка (иначе упрощение срезало бы дорогой грунт). Обычно 3–10 точек.

**Контроллер:** если ошибка курса > 0,6 рад — поворот на месте, иначе едем с П-регулятором по курсу; замедление перед финальной точкой; лимиты Burger (0,22 м/с; угловую ограничили 1,8 из 2,84 рад/с — меньше проскальзывания) и ограничение ускорений. Лидар: впереди < 0,35 м — сбавить, < 0,16 м — стоп. Нет прогресса 15 с → перепланировать (до 3 раз) → «не удалось».

**Положение робота:** путь берём из колёсной одометрии, **курс — из IMU**. Агент публикует поправку `map→odom`, поэтому в RViz робот и лидар стоят на карте правильно.

**Батарея:** агент сам оценивает расход на метр по наблюдениям `/did/battery` и перед каждой поездкой считает бюджет «туда + домой».

**Офлайн-симулятор, по 10 случайных сценариев каждого уровня (сценарий с координатами образцов):**

| Уровень | Образцы | Возврат | Столкновения | Опасные зоны | Остаток батареи |
|---|---|---|---|---|---|
| easy | 100 % | 10/10 | 0 | 0 | 48,1 |
| medium | 100 % | 10/10 | 0 | 0 | 39,2 |
| hard | 100 % | 10/10 | 0 | **11 заездов** | 32,8 |

**Находки (хорошо рассказывать — это «научная» часть):**
1. **Батарея выдаёт дорогой грунт.** Расход на метр по переездам в easy: 1,11 / **1,70** / 1,15 / 1,11 — скачок ровно на переезде через зону A (×3,4). Это основа гипотезы H1: карту стоимостей можно восстановить по расходу батареи.
2. **Курс одометрии уплывает** на разворотах: 0,1 рад к концу пути → у образца ошибка 0,28 м при радиусе сбора 0,30 (прошли впритык). Курс по IMU → ошибка 0,05 м, в 5 раз меньше.
3. **Одометрия «едет сквозь стену»:** когда робот упёрся в стену, колёса буксовали, и одометрия показала его в 7 м от реального места. Поэтому судья считает по истинной позе.
4. **Тест поймал реальный баг:** при малом заряде робот разряжался посреди переезда. Добавили проверку бюджета поездки.
5. **В hard агент 11 раз заехал в опасные зоны** — он о них пока не знает. Это ровно задача уровня 4 (адаптация).

## 10. Как использовали ИИ при разработке

- **Claude Code** как напарник-разработчик в терминале (WSL): план → маленький шаг → запуск и доказательство (тесты, `ros2 topic echo`, логи) → git-коммит → запись в DEVLOG.
- **Правила, которые мы ему задали:** сначала показать план и дождаться подтверждения; не ставить пакеты через sudo без спроса; не угадывать молча — неясности в QUESTIONS.md; логика без ROS и с тестами; всё запускается одной командой.
- **Что это дало:** 12+ коммитов за ~1,5 дня, 104 теста, журнал решений. Ассистент сам нашёл и объяснил: дрейф курса одометрии (по сравнению с истинной позой), падение RViz из-за драйвера видеокарты в WSL (шейдер карты → сброс GPU → чёрный экран), потерю имён в мосте ROS–Gazebo, конфликт имени `executor` с rclpy, падение узлов из-за int вместо float в цвете маркера.
- **Где человек решал сам:** выбор архитектуры и папки, разрешения на установку, визуальная проверка в окнах (ассистент не видит экран — он просил нас смотреть, а позже научился снимать скриншот окна RViz).
- **Доказательства для жюри:** [DEVLOG.md](../DEVLOG.md) (что, почему, какие грабли), история коммитов, [QUESTIONS.md](../QUESTIONS.md).

## 12. Вероятные вопросы жюри

- **Почему не Nav2?** Задание разрешает, но мы хотели свою карту стоимостей со слоем «грунтов», который обновляется по батарее (уровень 3), и полный контроль над логикой. Свой A* — 74 строки, покрыт тестами.
- **Строите ли вы карту сами?** Нет, используем статичную карту из пакета (задание это разрешает). SLAM — бонусный трек; лидар сейчас — для безопасности и визуальной проверки локализации.
- **Откуда агент знает координаты образцов?** На уровне 1 — из файла сценария, это явно помеченная временная мера («доехать по заданным координатам»). На уровне 3 — поиск по сигналу датчика (градиентный подъём/спираль), без координат.
- **Почему судья видит больше агента?** Судья — это «физика мира»: он считает по истинной позе из Gazebo. Агент видит только то, что положено по интерфейсу: одометрию, IMU, лидар, `/did/*`.
- **Где LLM?** Следующий шаг. Архитектура готова: LLM выдаёт подцели, исполнитель их проверяет (бюджет батареи, достижимость) — модель не может «уронить» робота.
- **Насколько надёжно?** 104 теста; 30 офлайн-миссий без столкновений; реальные прогоны easy/medium в Gazebo без штрафов.
- **Что было самым сложным?** Среда: Gazebo/RViz в WSL на Intel Arc (чёрный экран, артефакты) и неточность одометрии — оба решены и задокументированы.
